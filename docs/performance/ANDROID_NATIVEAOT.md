# Android NativeAOT validation

The NativeAOT work is separate from `android-v3.0.4`. Android 3.0.5 is the next
release target, subject to compatibility and packaging validation. macOS and iOS
product work is on hold.

## Runtime and serialization

Mono AOT and NativeAOT are different runtimes. Ordinary builds currently retain
Mono AOT; `EnableAndroidNativeAot=true` selects the experimental NativeAOT path and
an isolated `io.github.legends.otpharbor.nativeaotprobe` test identity. The test
manifest labels it **OTP Harbor AOT Test**, disables backups and cleartext traffic,
and keeps the normal biometric/camera permissions and file-provider boundaries.

Core preference, authorization-envelope and backup codecs, vault/profile payloads,
native account JSON import/export, and local icon-pack persistence/import now use
explicit source-generated JSON metadata. Existing serializer options, property
names/order, enum representations, depth limits, required members, duplicate and
unknown-field checks remain in place. .NET 10 source generation does not preserve
all omitted `init` property initializers, so preferences use an explicit JSON
constructor with the existing optional defaults. In particular, an older file
omitting app-lock settings continues to enable app lock.

The icon picker uses compiled bindings rather than a reflection binding subtree.
This preserves the shell command, item parameter, classes and displayed label.

## Security review

The change affects JSON contract discovery and managed-code execution. It does not
change encryption, KDF parameters, key wrappers, authorization decisions, storage
versions, signature verification or recovery policy. Generated contexts cache type
metadata rather than account values or secrets. Existing sensitive-buffer clearing
and fail-closed validation remain in their original call sites. The format has no
migration step: existing files must remain readable and new serialized JSON must
match the old contract byte for byte.

NativeAOT also trims code and changes Android runtime interop. Compilation alone
does not establish compatibility of JNI callbacks, camera, biometrics, encrypted
backups or activity recreation. Remaining platform-runtime diagnostics must remain
visible and be evaluated alongside functional tests; blanket warning suppression
is not part of this work. Microsoft still classifies Android NativeAOT as
[experimental](https://learn.microsoft.com/en-us/dotnet/android/messages/xa1040).

This change adds no icon acquisition or asset redistribution. Upstream collection
licenses do not grant trademark rights or override individual asset terms. Reviewed:
[Simple Icons disclaimer](https://github.com/simple-icons/simple-icons/blob/develop/DISCLAIMER.md),
[Aegis Icons](https://github.com/aegis-icons/aegis-icons), and
[Dashboard Icons license](https://www.dashboardicons.com/license). Existing asset
validation, attribution, provenance and user-responsibility wording are preserved.

## Repeatable local checks

```powershell
dotnet run --project scripts/testing/android/NativeAotCompatibilitySmoke -c Release

./scripts/testing/android/Build-AndroidAotExperiment.ps1 -Runtime NativeAOT `
  -NdkDirectory <path-to-ndk-28.2.13676358>
./scripts/testing/android/Build-AndroidAotExperiment.ps1 -Runtime Mono
```

The reflection-disabled smoke exercises preference defaults, authorization and
weak-KDF rejection, a complete 40-account vault/profile, legacy vault defaults,
backup configuration, v1/v2 backups and native JSON import. Unit tests also compare
generated bytes with the existing reflection-based contract. Headless tests cover
the complete account snapshot before reveal, native layout readiness, deferred
content, compiled picker bindings, recovery/retry, biometrics and recreation.

The two comparison APKs share a test package ID and test signing identity, allowing
data-preserving replacement with `adb install -r`. Verify package and certificate
identity before installation. Never uninstall or clear the test app between paired
measurements; never install a test-signed production-identity packaging fixture.
Use the same account/icon data and lock settings, alternate runtimes, exclude first
installation/setup and measure several cold process launches. Report account-ready
and visible-content timings separately from OS launch time and foreground resume.

## Current device evidence

An ARM64 NativeAOT APK was verified as non-debuggable, signed with the local test
certificate, installed under the isolated ID, and launched on the physical phone.
Initial empty onboarding reached visible content at 1,029 ms after
`Application.OnCreate`; Android reported initial display at 1,175 ms. A subsequent
launch with 17 accounts reached destination-ready at 370 ms and visible content
at 415 ms after `Application.OnCreate`. These stage timings exclude earlier OS
launch work. The user also reports startup under or near one second with 1,217
accounts. These are initial samples, not a measured paired Mono/NativeAOT speedup.

Before a production release, validate both universal APK architectures, all
protected workflows and the production signing pipeline with synthetic signing
inputs locally and the pinned production identity in Actions. A synthetic-signed
APK must never be published or installed as production. Await the user's remaining
phone workflow feedback and passing release checks before calling 3.0.5 ready.
